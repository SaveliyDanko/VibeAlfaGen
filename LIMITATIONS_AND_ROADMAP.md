# Ограничения решения и план развития после хакатона

## Ограничения текущего решения

- **Распознавание основано на правилах.** Встроенные детекторы используют
  регулярные выражения, проверки формата и контекст. ML/NER-модели нет:
  нестандартные записи, неоднозначные ФИО и адреса могут быть пропущены,
  возможны ложные срабатывания. Поддержка 17 категорий не означает
  распознавание всех вариантов персональных данных на любом языке.
- **Полнота маскирования зависит от политики.** `detect_types`, `mask_types`
  и условные `rules` могут оставлять часть данных открытой. Режим `format`
  сохраняет разделители и для некоторых типов часть исходных символов;
  для непрозрачной замены предусмотрен `token`.
- **Восстановление требует сохранённого контекста.** В Docker соответствия
  хранятся в Redis в зашифрованном виде с TTL 30 минут по умолчанию.
  После истечения TTL, удаления данных или потери ключа шифрования
  восстановить исходник по маске нельзя. Redis — часть рабочего решения;
  недоступное хранилище не заменяется автоматически памятью backend.
- **`/process` работает с конкретной парой текстов.** Для одной системы
  `payload_id` связывает исходник и его маску: повтор исходника возвращает
  прежнюю маску, передача этой маски — исходник. Пока контекст существует,
  третий текст с тем же ID вызывает HTTP 409. Для нового текста нужен новый ID.
- **Обработка синхронная и текстовая.** API принимает JSON с текстом;
  извлечения текста из PDF, изображений и OCR, потоковой обработки и
  очереди пакетных заданий нет. В Compose тело запроса ограничено 2 MiB
  (включая JSON), `request_timeout` — 10 секунд, `concurrency_limit` — 256.
  Это настройки текущего стенда, а не обещание времени обработки любого текста.
- **Локальный вызов LLM демонстрационный.** `/v1/generate` работает в режиме
  `test_generate` с Mock LLM; `/process` внешний провайдер не нужен.
  Автоматического выбора нескольких провайдеров по системе пока нет.
- **Горячая перезагрузка ограничена политиками систем.** Изменения `systems`
  применяются с новой `version`. Новые `custom_pii_types`, ключи шифрования,
  настройки сервера, Redis и провайдера требуют перезапуска backend.
  Для нового Go-детектора нужна пересборка образа.
- **Compose рассчитан на один узел.** В поставке один backend и один Redis,
  без автоматического переключения при отказе и автоскалирования.
  Redis использует AOF и локальный volume, но автоматического резервного
  копирования нет. Лимит памяти Redis по умолчанию — `3gb` с `noeviction`:
  при его достижении новые контексты не сохраняются, а старые не вытесняются.
- **Замеры имеют ограниченную область применимости.** Исторические RPS
  получены на конкретных конфигурациях и размерах текста; крупные документы
  измерялись отдельно. p50 в Grafana относится к PII-модулю, HTTP-задержка —
  к нагрузочному отчёту, TPS оценивается по байтам. Условия и результаты
  приведены в [разделе производительности](PERFORMANCE_AND_FEATURES.md).

## План развития после хакатона

Ниже — направления дальнейшего развития, а не реализованные возможности
или утверждённые сроки. Сохранены все направления из исходной ветки
документации. Текущие настройки описаны в
[архитектуре](ARCHITECTURE_AND_CONFIGURATION.md), реализованные дополнения —
в [обзоре возможностей](PERFORMANCE_AND_FEATURES.md).

### Развитие продукта

1. **ML/NER-детектор** поверх текущего regex-слоя для случаев, которые
   плохо формализуются паттерном — нестандартные ФИО, редкие форматы
   адреса, тексты на других языках.
2. **Расширенный набор распознаваемых документов и категорий ПД**:
   загранпаспорт, СНИЛС, ID-карта, полис ОМС/ДМС, банковские реквизиты
   помимо номера карты (БИК, расчётный счёт) — сверх уже реализованного
   водительского удостоверения и 17 базовых категорий.
3. **Полноценный plugin-реестр кастомных типов ПД**: композитные детекторы
   (несколько сигналов на один тип, а не только одно регулярное выражение),
   внешний источник правил с загрузкой без перезапуска процесса, UI/CLI для
   администратора поверх уже работающего механизма `custom_pii_types`, без
   необходимости редактировать YAML-конфиг руками.
4. **Синтетическая замена данных** (`mask_mode: synthetic`) как альтернатива
   токенизации — офлайн-справочник правдоподобных фейковых значений расширил
   бы выбор вида маскирования по системе.
5. **Горячая ротация ключей шифрования** с фоновым перешифрованием
   сохранённых контекстов. Сейчас ключи задаются при старте; старые ключи
   нужны до истечения срока жизни зашифрованных ими записей.
6. **Клиентские SDK** для популярных языков (Python, Node.js, Java) поверх
   HTTP API `/process`, чтобы интеграция не требовала писать HTTP-клиент и
   разбирать формат ответа вручную.
7. **Поддержка нескольких LLM-провайдеров в `/v1/generate` "из коробки"**
   (сейчас — Mock LLM или один настроенный provider), с выбором провайдера
   per-system, аналогично уже реализованному выбору `mask_mode` per-system.
8. **Расширение версионирования и аудита политик**: дополнить существующие
   версию конфигурации и журнал действий админки историей полных политик,
   откатом к предыдущей версии и экспортом безопасных событий обнаружения.

### Масштабирование под более высокую нагрузку

9. **Multi-node Redis (Sentinel/Cluster)** вместо единственного узла —
    репликация, автоматический failover, шардирование контекстов по
    системе или hash от `payload_id`, чтобы рост RPS не упирался в один
    Redis-инстанс.
10. **Горизонтальное автоскалирование backend** (Kubernetes HPA по CPU или
    по RPS/latency-метрикам). В текущем Compose работает один backend;
    управление репликами и Kubernetes-развёртывание потребуют отдельной
    конфигурации.
11. **Потоковая/чанкованная обработка очень больших документов** — сверх уже
    проверенных 100 000 токенов текст можно обрабатывать частями, не
    загружая целиком в память. Для этого потребуются отдельный потоковый API
    и пересмотр `max_body_bytes`. Цель — обрабатывать большие тексты без линейного роста
    памяти на запрос.
12. **Снижение протокольных накладных расходов на высокой частоте запросов**:
    оценить переход на HTTP/2 или gRPC и бинарный формат (protobuf) вместо
    JSON для интеграций с большим RPS, где сериализация становится заметной
    долей latency.
13. **Гео-распределённое развёртывание** (несколько регионов/edge-точек) для
    систем-потребителей с жёсткими требованиями к latency, с учётом
    согласованности контекстов маскирования между регионами.
14. **Асинхронный batch-режим обработки** для массовой маскировки большого
    количества документов одним заданием (очередь + воркеры), как
    альтернатива синхронному HTTP-вызову на каждый документ.
